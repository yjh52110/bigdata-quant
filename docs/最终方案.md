# 最终方案

每个决定后面都附了当初做这个决定的实测依据。没有实测支撑的地方，标了「未验证」。

测量日期：2026-07-25 / 07-26。

---

## 一、整体形状

```
用户（Codex / Claude 等 app）
        │  MCP 协议
        ▼
   FastMCP 服务（必须常驻公网）
        │
        ├── scheduler.py    算策略：几路并发、写哪些账号、受什么限制
        │
        └── Dagster         执行：分区回填、断点续传、失败重试、限并发
                │
        ┌───────┴────────┐
        ▼                ▼
   Colab（3 路）    Kaggle（≥5 路）
        │                │
        └───────┬────────┘
                ▼
          Google 云盘（多账号）
                ▲
                │  原地查询，不搬运
          AWS S3 公开数据集（61.31 TB）
```

## 二、数据存两处，各有各的理由

| | 存哪 | 为什么 |
|---|---|---|
| **原始链上数据** | **云盘归档 + S3 原地查，两者都要** | 见下 |
| 派生因子 / 信号 | 云盘 L2 / L3 | 自己算的，别处没有 |
| 爬来的数据 | 云盘 L1 | 不采就永远没了 |

**为什么原始数据既要归档又要原地查**，两个需求不同：

- **原地查**用于探索。实测单列查询只传文件的 0.29%，S3 上 43–324 MB/s，比从云盘读回（29.96 MB/s）更快更细。为查询而复制是净亏损。
- **归档**用于可复现与不可变。AWS 公开数据集靠赞助，其中 5 条链是第三方维护；上游改写一个分区，去年的回测今年就对不上。量化研究要求数据钉死不动。

重压能省一半：AWS 用 snappy，同一天 eth transactions 实测 1408 MB → zstd 739 MB。**全量 61.31 TB → 约 32 TB**，7 个账号装得下。

## 三、存储格式：四条硬规则

| 规则 | 实测依据 |
|---|---|
| **zstd** | 同一份数据：不压缩 2215 MB / snappy 1408 MB / **zstd 739 MB**，解压只多 0.07s |
| **单文件 200–500 MB** | 200 MB 传 36.56 MB/s，5.9 MB 只有 1.53 MB/s —— **差 24 倍**，且每次读都要再付一遍 |
| **文件内按时间排序** | 否则行组 min/max 覆盖整个分区，谓词下推一个组都跳不掉 |
| **数据集不跨账号拆分** | 拆了每次读要多令牌扇出，而单个数据集只有几十到几百 MB |

按排序方式还能再省 16%（按地址排 36.01 MB vs 按时间排 43.01 MB），但那会牺牲按时间查的跳过能力，**取决于主要按什么查，不能盲目换**。

### 目录布局

```
chainquant/
├── L1_normalized/   domain=chain/chain=eth/table=blocks/date=2024-01-15/
│                    domain=market/exchange=binance/symbol=BTCUSDT/interval=1m/
│                    domain=news/source=coindesk/date=2024-01/
├── L2_features/     name=addr_flow_1d/date=2024-01/
├── L3_signals/      strategy=xxx/date=2024-01/
└── _catalog/        datasets.json + shards/
```

按**提炼阶段**分层而不是按数据源：七类源最终都走同一条净化→提炼路径，按阶段分只需一套约定。

## 四、目录清单是必需品，不是优化

`drive.file` 范围只能看见本应用创建的文件，**没有浏览兜底**，而 Drive 列目录慢到会主导一次 MCP 调用的延迟。

14 个字段，其中 `account` 只存在于清单里 —— 丢了就得逐个账号搜。所以清单会**备份到云盘**（1 KB 级），且备份是覆盖而非累积：过期的清单比没有清单更糟。

---

## 五、并发：不用锁，让并发方从一开始就不碰同一份东西

云盘没有抢锁可用，所以五处竞争全部用「分区」解决：

| 竞争 | 实测症状 | 解法 |
|---|---|---|
| 同名文件夹 | 云盘**允许**同名，两个会话各建一个，数据一半进一个 | 都取最小 ID，收敛到同一个 |
| 清单条目 | 读-改-写，后保存的抹掉前者 | 每写入方一个分片文件，读时合并 |
| 文件名 | 两会话都从 part-00000 开始，**B 覆盖了 A** | 文件名带写入方标识 |
| 账号选择 | 都挤最空的账号，撑爆一个而其余闲置 | 按写入方哈希偏移分散 |
| 爬虫领任务 | 两爬虫**领到同一个 URL** | URL 按哈希分片，各管一片 |

比加锁更可靠：没有死锁、没有超时。

**限制**：爬虫分片数改变会导致漏抓/重抓，要改得等当前批次跑完。

## 六、计算：跨平台，不是多账号

| 平台 | 并发 | 精确度 |
|---|---|---|
| Colab | **3** | 精确（第 4 个报 `Precondition Failed`） |
| Kaggle | **≥5** | **下限**，真实上限未触及 |

**多账号不是合法的计算扩展轴**：Colab FAQ 原文把「用多账号绕过资源限制」列为禁止行为；Kaggle 的 GPU 与联网都要手机验证。

**存储侧的多账号是合法的**，那才是大任务的解法。

### 实测速率

| 项 | 值 |
|---|---|
| 单会话上传云盘 | Colab 35.61 / Kaggle 36.56 MB/s（**几乎相同 → 云盘侧限制**） |
| 5 会话并发上传 | 各 31.78 MB/s（低 13%），聚合约 159 MB/s |
| 8 会话跨平台聚合 | 约 265 MB/s |
| 云盘读回（顺序） | 29.96 MB/s 本机 / 55.86 MB/s Kaggle 内 |
| **分段下载最优** | **2 路 119.3 MB/s**，4/8/16 路反而降到 112/107/98 |
| S3 → Kaggle | 324.5 MB/s |
| DuckDB 聚合 | 简单 743 MB/s、高基数 160 MB/s、窗口 119 MB/s |

分段下载那条有个教训：同样的测试在家宽上峰值在 8 路且只 1.6 倍（瓶颈是管道本身 1.8 MB/s）。**同一实验在不同链路给出相反的最优值**，所以这个常量注明了属于机房链路。

## 七、真正的瓶颈是每日配额，不是速度

按 265 MB/s，32 TB 只需 35 小时。但**云盘每账号每天最多上传 750 GB**，满速跑 47 分钟就到顶。

| 账号数 | 32 TB 需要 |
|---|---|
| 7 | 6.2 天 |
| 15 | 3 天 |
| 43 | 1 天 |

**并发的价值是「更快用完每个账号当天的份额」，不是提高总量。**

## 八、采集：三种模式，poll 再分两种策略

| 模式 | 含义 | 占云盘 |
|---|---|---|
| `in_place` | 原处已是分析就绪格式，查它比搬它划算 | ❌ |
| `batch` | 周期性归档，按周期幂等 | ✅ |
| `poll` + `pump` | 沿游标把接口抽干；约束是速率限制 | ✅ |
| `poll` + `watch` | 只取增量、只存没见过的；产出零碎，依赖合并 | ✅ |

多数方案默认「数据都得先搬进来」，`in_place` 是这套方案比标准做法更省的地方。

三条防丢数据的性质：**游标写在记录之后**（先推进再崩溃会静默跳过在途数据）、**状态在磁盘上**（运行时 12 小时封顶）、**服务端 Retry-After 压过本地配置**（并封顶以防坏 header 挂死）。

### 采集侧三原语（Apify 形状）

`Dataset`（缓冲后合并成合规文件）、`KVStore`（小 blob 打包进 BLOB 列、大的独立 + 键索引）、`RequestQueue`（去重、重试、落盘续爬）。

## 九、编排：scheduler 出策略，Dagster 出执行

`DailyPartitionsDefinition` + `BackfillPolicy.multi_run(max_partitions_per_run=8)` + `RetryPolicy` —— **「4014 个日分区、可续传、并发不超 8」是配置，不是项目。**

Dagster 不可能知道云盘每账号 750 GB/天，也不知道分段下载最优 2 路。**实测常量留在 scheduler 里，资产只去问它该开多宽。**

已实测：一个分区端到端 32 秒（S3 读 → zstd 重编码排序 → 上传 → 登记清单），7159 行 / 3.19 MB。

**代价**：`omegaconf` 钉死 `antlr4==4.9.*` 而 Dagster 需要 4.13，两者不可两全，编排层用独立虚拟环境 `.venv-orch`。`backfill_policy` 仍是 beta 参数。

## 十、云盘能做什么、不能做什么

| | 能 | 依据 |
|---|---|---|
| 存文件 | ✅ | |
| 被 DuckDB 原地查 | ✅ | 实测 113 万行，不下载整文件 |
| Range 分段读 | ✅ | HTTP 206，`Content-Range 0-1048575/209715200` |
| 变成 DuckLake / 数据库 | ❌ | 实测 `Writing to HTTP files not implemented` |
| 原子提交 / 时间旅行 | ❌ | 云盘没有条件写，**结构性做不到** |

要这些能力必须换底座（R2 32 TB 约 $480/月，云盘为 0）。**折中**：因子与信号（GB 级、反复读、需要版本）放对象存储，每月几美元；原始数据留云盘。

## 十二、还没做的

| 缺口 | 说明 |
|---|---|
| **反馈调优** | 实测 5 会话速率 23.58–39.45 MB/s（差 1.67 倍），现在平均分片，被最慢的拖着 |
| **MCP 编排** | 任务拆解、体积预估、优先级抢占、用量归因 —— 收费闭环需要 |
| 32 TB 归档实跑 | 已验证一个分区，未跑全量 |
| Colab 侧云盘密钥 | 需用户手动粘贴一次（令牌类不代为输入） |
| ABI 解码层 | 把 logs/traces 从十六进制变成语义 |
| 策略挖掘 | 用户明确暂缓 |

---

## 建议的执行顺序

1. **先归档第一层 4 TB**（eth 全部不含 traces + btc + bnb），3 个账号约 2 天
2. 跑通后补 **MCP 编排**，让 Codex 里的一句话能驱动整条链路
3. 需要实时监控时，走 **历史用 S3 + 实时用 RPC 订阅** 的混合方案
4. 数据成为收入来源后，再评估把 L2/L3 迁到对象存储换取时间旅行
